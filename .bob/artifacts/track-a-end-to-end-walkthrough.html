The runner does a single batch insert. The proxy also inserts a row for every request it proxies — including the flip event.

Runner rows: service = "stable" or "canary"  ·  Proxy rows: service = "proxy->stable" or "proxy->canary"  ·  Flip rows: service = "proxy"
DB CHECK constraint (migration 0002) enforces that service is always one of 'stable', 'canary', 'proxy', or 'proxy->*'. A writer using a wrong string is rejected by Postgres, not silently stored. 
-- supabase/migrations/0002_service_check.sql
alter table logs
  add constraint logs_service_check
  check (
    service in ('stable', 'canary', 'proxy')
    or service like 'proxy->%'
  );

Rule 1 — 5xx error check (critical endpoints)
# canary has errors, stable does not
c_err = [rows where
  service == "canary"
  and "/checkout" in endpoint
  and status_code >= 500
]  # → 1 row

s_err = []  # stable had 0 errors

if c_err and not s_err:
    reasons.append(

# stable p95 ≈ 8ms, canary p95 ≈ 820ms

c_p95 = 820

if c_p95 > s_p95 * 2.0:  # 820 > 16 ✓

7
agent Proposals — derived from the reasons
POST :8003/propose — calls decide() internally, passes the reasons to build_proposals(). Only actionable proposals are returned.
Because both bugs triggered (5xx + latency), has_5xx = True so only the primary executable proposal is returned — no informational clutter. The 5xx alone is enough to flip back to stable.
